# GitHub App setup pilot for release workflows

Status on 2026-11-19. Discovery and acceptance specification for [issue #2](https://github.com/zima-oss/jackstay/issues/2). The organization pilot has verified manifest registration, a scoped installation and a token read probe in a dedicated private test repository.

## Scope and existing contract

`jst adopt` writes a release workflow that reads `JACKSTAY_RELEASE_APP_CLIENT_ID` from Actions variables and `JACKSTAY_RELEASE_APP_PRIVATE_KEY` from Actions secrets. It calls `actions/create-github-app-token` v3.3.0 with `client-id` and `private-key`, then uses the token to run `jst release publish` and `jst release pr`. The workflow currently takes the action's default current-repository token scope and does not explicitly reduce its permissions. [Release template](../../internal/adopt/templates/files/release.yml) · [Action inputs](https://github.com/actions/create-github-app-token#inputs)

The proposed command is an **optional** `jst github app setup` integration. Its first implementation should work with one selected owner and repository. The plan must state the account, repository, App name, requested permissions, settings destinations, credential handoff and human GitHub steps before any write. A nonterminal invocation reports the plan and a finding identifier through the existing `jst setup --plan --json` reporting model. An interactive invocation pauses for the App registration and installation steps. The local project configuration and adoption of its release workflow remain separate. [Issue #2](https://github.com/zima-oss/jackstay/issues/2) · [Machine setup](../guide/install.md#plan-machine-setup)

The first permission set to test is repository `contents: write`, `pull_requests: write` and `metadata: read`, with no events or active webhook. Request `workflows: write` only after a fixture demonstrates a release operation that edits `.github/workflows`. The release workflow currently does not request that permission. GitHub documents that `workflows` permission updates workflow files, while `contents` covers Git operations and release creation. Endpoint permissions and the effective installation grant still need to be measured in the pilot. [Issue #2](https://github.com/zima-oss/jackstay/issues/2) · [GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app) · [REST permission names](https://docs.github.com/en/rest/apps/apps)

## Proposed registration and credential flow

1. Resolve the authenticated GitHub owner and the exact target repository. Refuse an owner or repository mismatch and an existing App of the same intended name until the operator selects a recovery path. Show both the organization and personal-account storage plan before registration. For an organization, expose the Actions variable and secret only to selected repositories. For a personal account, store them on each selected repository. GitHub CLI supports both repository settings and selected-repository organization settings. [CLI variables](https://cli.github.com/manual/gh_variable_set) · [CLI secrets](https://cli.github.com/manual/gh_secret_set)
2. Start the manifest registration with `public: false`, `default_events: []`, an inactive webhook, the minimal permissions, a redirect URL and a random `state`. The form posts to the personal or organization GitHub App settings endpoint. GitHub sends a temporary `code` and the original `state` to the redirect URL. Accept the code only when the state matches and the local session is waiting for that exact owner. Complete conversion within GitHub's one-hour window. A loopback listener is the preferred pilot candidate, but its redirect behavior on both account types must be confirmed before implementation. [Manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)
3. Exchange the code once through `POST /app-manifests/{code}/conversions`. Consume the response in memory, suppress HTTP and process logging, and send only the private key through the secret writer's standard input. Store the returned client ID as the named variable. Never place the code, private key, webhook secret, client secret or installation token in command arguments, files, environment dumps, receipt records or user-visible plans. A retry after an uncertain conversion result must inspect the App registration and stored settings instead of blindly exchanging the code or registering another App. The conversion response includes the App ID, slug, client ID and PEM key. [Conversion API](https://docs.github.com/en/rest/apps/apps#create-a-github-app-from-a-manifest) · [CLI secret input](https://cli.github.com/manual/gh_secret_set)
4. Present GitHub's installation link and require the owner to choose **Only select repositories**. Verify the App identity and repository list through the installation API before publishing a ready result. A listed variable and secret prove presence only, since GitHub does not return secret values. Generate a repository-scoped token with the new key, check that it can read the target repository and cannot read a second disposable repository, then revoke it. The normal action revokes its token at the end of the job. [Install your App](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app) · [Installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) · [Action behavior](https://github.com/actions/create-github-app-token#how-it-works)
5. Mark `jst doctor` ready only after it finds the adopted release workflow, both setting names, an App installation covering the intended repository and a successful bounded token probe. Report missing, inaccessible and unknown separately. A noninteractive or offline check may report the local facts and `unknown` for the remote probe. It must not claim that a secret's name proves its key works. [Issue #2](https://github.com/zima-oss/jackstay/issues/2) · [CLI secret listing](https://cli.github.com/manual/gh_secret_list)

## Disposable pilot acceptance matrix

### Personal-account prerequisite run

A dedicated private test repository under a personal account had an admin grant and Actions enabled. The probe used an empty synthetic repository.

| Probe | Observed result |
|---|---|
| `gh variable set` in the dedicated repository | A synthetic `JACKSTAY_PILOT_CLIENT_ID` variable was written and read back through the repository Actions variable API. Its value is only a placeholder. |
| `gh secret set` from standard input in the dedicated repository | A synthetic `JACKSTAY_PILOT_FAKE_PRIVATE_KEY` secret was accepted. The repository Actions secret API returned its name and creation timestamp. GitHub did not return the value, so this proves storage metadata only. |
| Repository installation endpoint with the current user token | `GET /repos/{owner}/{repo}/installation` returned HTTP 401 with `A JSON web token could not be decoded`. This endpoint requires App authentication for this query; the response does not establish whether an App is installed. |
| User installations endpoint with the current user token | `GET /user/installations` returned HTTP 403 and requested a token authorized to a GitHub App. The present CLI credential cannot perform the planned installation check through that endpoint. |

The synthetic variable and secret from the earlier prerequisite probe use distinct names. That probe covered storage metadata and the CLI token's installation-query limitations.

A separate organization pilot created one empty private repository through its OpenTofu stack.
The owner confirmed registration in GitHub's manifest flow and installed the private App on
the selected pilot repository. The loopback callback verified its state and exchanged the code
over verified TLS. It passed the returned private key in memory to the pilot repository's
Actions secret, and stored the client ID in its Actions variable. A narrowed installation
token listed exactly one repository, read that target and was revoked after the probe.

A workflow in that same test repository minted a fresh scoped App token from the saved Actions
settings, checked its one-repository grant, pushed a synthetic Git branch and created a pull
request. A second workflow triggered from that App-authored pull request and passed. A preceding
REST contents write directly after ref creation returned HTTP 404. The successful Git push
exercised the same write surface as release delivery. The pilot used repository-scoped Actions
settings and no production workflows.

Use a disposable organization repository, a second unrelated repository under that organization, and a disposable personal-account repository. Each fixture has its own App and branch or tag ruleset where needed. Keep account identifiers, private repository paths and raw object IDs in operator-controlled notes outside Git. Publish sanitized outcomes and status codes. Keep credentials and temporary registration codes out of notes and logs. Delete pilot credentials and Apps after the evidence is reviewed.

| Case | Pilot operation | Pass evidence | Refusal or recovery check |
|---|---|---|---|
| Manifest registration | Register one private App for the organization through the proposed redirect; repeat for a personal account | Returned slug, client ID and App ID match the chosen owner; callback state matches; conversion finishes within one hour | Wrong state, expired code, second conversion and lost callback produce a specific recoverable state without leaking response data |
| Permissions | Install with the three proposed repository permissions on the target only | Installation and a narrowed token show the requested grants; PR update, release commit, tag and release API operations succeed in the disposable repository | Remove `pull_requests` or `contents` in a second fixture; the relevant operation fails with a diagnosable permission result. Workflow file edits are tested separately before considering `workflows: write` |
| Storage | Write the client ID and PEM to selected-repository organization Actions settings; repeat with repository settings for the personal account | Variable equals the conversion client ID; secret name, visibility and selected repository IDs are correct; token creation succeeds in the target workflow | A secret absent, wrong client ID, denied org scope or wrong selected-repository list produces a failed readiness check. No key material appears in logs or the repository |
| Installation boundary | Install on target only and request a token restricted to that repository | Target read succeeds, unrelated repository read fails, and token revocation is observed | Installation absent or all-repositories selection produces an explicit mismatch against the requested plan |
| Ruleset | Give the App an **Always allow** bypass on a disposable protected base branch, then push a release commit and create a tag with its token | Ruleset reports the selected App; push and tag succeed while the same operations with an unauthorized actor fail | A **For pull requests only** bypass must not be treated as authority for jackstay's direct release commit |
| Follow-on workflows | Use the App token to push a release commit and to open or update a pull request in the target repository; create a fixture operation in a second selected repository | Record the actual `push` and `pull_request` workflow run IDs and triggering actor for each operation | If a cross-repository workflow does not start, or starts only after approval, keep that behavior documented and do not claim general workflow triggering |
| Dependabot | Trigger the release workflow from a disposable Dependabot update | The App-token step is skipped and no release write is attempted | An empty `client-id` or missing Actions secret must not turn the run into an attempted release |
| Restart | Interrupt after registration, conversion, variable write, secret write and installation independently | Re-entering the same plan reports the observed phase and completes at most one App and one configured installation | Unknown remote effects stop for reconciliation instead of overwriting a key or creating a duplicate App |
| Rotation | Add a second App key, replace every selected secret, verify a new token, then delete the old key | Existing workflows stay able to mint tokens during the transition; old key fails after deletion; selected repository list remains the same | Failed secret update leaves the old key valid until repaired; no partial rotation is called complete |

The ruleset and workflow cases are experiments. GitHub documents App bypass actors and the difference between **Always allow** and **For pull requests only**. It also documents that ordinary events produced with `GITHUB_TOKEN` usually do not start workflows, with exceptions for dispatch events and some pull request activity. The issue's broader statement about all `GITHUB_TOKEN` events therefore needs this targeted measurement, especially across repositories. [Ruleset bypass](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) · [GITHUB_TOKEN triggers](https://docs.github.com/en/actions/concepts/security/github_token)

## Implementation sequence and release gate

1. Capture the pilot's API and workflow observations, including personal-account conversion, loopback redirect, selected repository visibility, permission responses, cross-repository triggers and ruleset bypass. A real GitHub run is needed for these claims. Fake API responses alone cannot settle them.
2. Review the credential path before implementing conversion. The review covers callback CSRF state, one-hour codes, response-body handling, process arguments, logging, secret writer failure, recovery after uncertain remote effects, token revocation and rotation. GitHub recommends overlapping keys for rotation. [Manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) · [Private key rotation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)
3. Build the no-terminal plan and local fake-provider tests using the `jst setup` finding format. Then add the interactive registration and organization/personal storage paths. Add `jst doctor` readiness only after the live pilot establishes which checks can be performed with the user's available credentials. Confirm installation and scope before any release workflow change.
4. Update the adopted release workflow to scope its App token to the target repository and required permissions, skip Dependabot-triggered writes, and avoid checkout credentials persisting. Regenerate adoption goldens, run `jst adopt --plan` here, and exercise the disposable release workflow end to end. The action supports `repositories` and `permission-*` inputs. GitHub excludes Actions secrets from Dependabot-triggered workflows. [Action inputs](https://github.com/actions/create-github-app-token#inputs) · [Dependabot secrets](https://docs.github.com/en/code-security/reference/secret-security/secret-types)
5. Run package and integration tests, `just gate` on macOS and Linux, and a fresh disposable-repository pilot with no saved App settings. The feature is ready only when every matrix case has a recorded result, the key remains absent from repository and logs, and `jst doctor` distinguishes ready, missing and unknown states.

Open proof cases include ruleset bypass, release workflow edits, cross-repository triggers, personal-account manifest conversion and key rotation. The organization loopback flow already passed. These results determine the final command behavior. [Issue #2](https://github.com/zima-oss/jackstay/issues/2)
